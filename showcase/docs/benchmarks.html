Benchmark evidence and methodology

Performance is a measured claim about a particular implementation, workload, host and revision—not a promise for every user.

Interactive resultsRegression policy

Evidence campaigns

The published GitHub Actions campaign contains 22 paired cases covering eight modules. A separate local VM campaign contains 16 cases. Do not combine absolute times between the two hosts.

Interpret numbers responsibly

  • Compare only identical inputs and output checksums, with the same host, toolchain and flags for each pair.
  • Publish losses and ties as prominently as wins.
  • Process peak RSS is not isolated library memory usage.
  • Microbenchmark latency excludes application-level I/O, allocations and scheduling unless explicitly stated.
  • GitHub-hosted runner variance can be substantial; investigate failures rather than weakening protected thresholds.

Reproduce a local benchmark

cmake -S . -B build-bench -DCMAKE_BUILD_TYPE=Release -DNEWTON_BUILD_BENCHMARKS=ON
cmake --build build-bench --parallel
# Run the relevant benchmark binary using its documented flags.

Exact external comparisons and reproducible fixtures: benchmark harness guide. Provenance and limitations: capability scorecard.

Guard policy. The existing regression checker uses five alternating rounds, eleven inner repetitions and a 3% paired-median limit confirmed by at least four slow rounds, plus its independent CSV pipeline checks. No published benchmark threshold is changed by this site.
